**Root cause (from `run_info.json` `call` strings):** each `LGSOC_P#` kallisto run was invoked with **FASTQs from multiple different biological samples merged together and with mismatched R1/R2 mate pairs**. ## 4. Assay B — Whole-exome sequencing (WES)

Two directories reflect **two analysis modules of the same nf-core/Sarek-style pipeline**, not two versions of the same output. Both cover the **same 23 samples at the same passages** (passage embedded in filenames; verified identical between modules).

### "new" — CNVkit copy number: `judy_archive/data/cnvkit wes - new/`
- **Tool:** CNVkit **v0.9.10** (apptainer), reference **GRCh38 (GATK Homo_sapiens_assembly38)**, WES target/antitarget BED intervals, `--drop-low-coverage`, `--diagram --scatter`. Commands preserved in `commands.txt` (23 `batch` calls) and `command_diagram.txt` (17 diagram calls).
- **Per-sample outputs** (`*_new/` dirs): `.cnr` (bin log2), `.cns` / `.call.cns` / `.bintest.cns` (segments/integer calls), `.targetcoverage.cnn` / `.antitargetcoverage.cnn`, `reference.cnn`, `-diagram.pdf`, `-scatter.png`, plus a copy of `intervals_sorted.target.bed`.
- **Normal reference (verified — see "old vs new" analysis below):** a single pooled `reference.cnn` built from **5 public healthy germline WXS exomes — SRR4039087/88/89/96/97**, applied uniformly to all 23 tumors. `reference.cnn` is **byte-identical (md5 `f6de5ce5…`) across every sample dir**, confirming one shared reference. The 5 normals are `Normal_Ker2/6/7/…` from **BioProject PRJNA339046, "The Genomic Landscape of Atypical Fibroxanthoma"** (Homo sapiens, WXS, GENOMIC) — i.e. unrelated public normal-skin exomes, not matched ovarian normals. Only `normal_samples/SRR4039087/SRR4039087.bam` (461 MB) is archived; the other 4 survive only as pre-computed coverage `.cnn`.
- **Folder organization (misleadingly named):** `All samples/` holds 13 dirs; `CC/` (2), `EC/` (1), `HGS/` (9) are subtype-regroupings of 12 of those 13 (mucinous TOV2414 uncategorized); **6 loose top-level `*_new` dirs** (OV3133_R2_P58, OV3291_P46, TOV2835EP_P64, TOV3121D_P68, TOV3121EP_P68, TOV3133D_P66) and **`20251208 - new samples/`** (4: TOV2295_R_P57, TOV2881EP_P64, TOV2929D_P57, TOV81D_P23) are **not** in "All samples." "All samples" is therefore a subset, not the full set. CC/EC/HGS appear to be duplicate copies (storage redundancy).

### "old" — Mutect2 mutations: `judy_archive/data/wes - old/mutect2/`
- 23 per-sample dirs (+ `mutect2.zip`). Per sample: `{sample}.mutect2.filtered_VEP.ann.vcf` (VEP-annotated, filtered SNV/indel), `.vcf.gz.tbi` (tabix index), and `{sample}.maf`.

### "old" vs "new" — reference construction (verified from files)

The PI's recollection was that the "new" CNVkit runs used a healthy diploid normal reference while the "old" runs used a flat/pooled reference (making "new" more reliable). **Checking the files refines this:**

**(a) What reference each set used.**
- **"new" (CNVkit CN):** empirically **normal-referenced**. All 23 `cnvkit.py batch` calls in `commands.txt` pass `-n normal_samples/all_bams/*.bam` (a real set of normal BAMs) — never an empty `-n` (which is how CNVkit builds a *flat* reference). The `-f Homo_sapiens_assembly38.fasta` is the genome, not a flat reference. Only two subcommands appear (`batch` ×23, `diagram` ×17); there is **no standalone `cnvkit.py reference` and no flat-reference invocation**. The reference is the 5 pooled healthy germline exomes described above, **built once and shared byte-for-byte** across all 23 tumors. So the "new" set is genuinely normal-referenced (a valid copy-number-neutral baseline), consistent with the PI.
- **"old":** **there is NO copy-number output in the archive at all.** `wes - old/` contains **only Mutect2** SNV/indel calls (per-sample VCF/MAF/tbi) and `mutect2.zip` (also mutation-only — verified: zip holds vcf.gz/tbi/tsv/stats/maf, zero `.cn[rs]`/`.cnn`/cnvkit entries). No `.cns/.cnr/.cnn` exists anywhere outside `cnvkit wes - new/` (only a downstream figure, `figs/Figure 3/3c_cnvkit_heatmap.pdf`, which is derived from the "new" calls).

  **Therefore the archive's "old vs new" is not "flat-ref CNV vs normal-ref CNV" — it is "Mutect2 mutations (old module)" vs "CNVkit copy number (new module)," two modules of one Sarek-style pipeline.** If an earlier flat-reference CNVkit run ever existed, **it was not retained** and cannot be inspected here. The claim that "old CNV used a flat reference" is thus **not file-verifiable** — flag for the PI to confirm from message/pipeline history.

**(b) Sample overlap.** The Mutect2 ("old") and CNVkit ("new") modules cover the **identical 23 samples at identical passages** (verified by matching the passage embedded in every filename). **No old-only or new-only CN samples exist** (there is only one CN call set). The single file-level asymmetry: `TOV3121D_P68` has CNVkit CN + a Mutect2 VCF but **no MAF**.

**(c) Recommendation.** Treat the **"new" CNVkit calls as canonical** for copy number — they are the only CN set present, are properly normal-referenced (not flat), use a single shared pooled reference, and back the manuscript's Figure 3c. **Caveat to document in Methods:** the normal panel is 5 *unmatched public exomes from a skin-cancer study* (PRJNA339046), not matched ovarian/germline normals from the same capture kit; if the tumors' exome capture kit differs from that study's, the pooled reference can introduce target/capture bias in the log2 ratios. Recommend (i) confirming capture-kit concordance between tumors and the SRR normals, and (ii) retiring the "old/new" labels in favor of "Mutect2 (SNV/indel)" and "CNVkit (copy number)" to avoid implying two competing CN versions. No reconciliation between an old and new CN set is needed because only one CN set exists.
